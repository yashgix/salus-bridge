An agent's refund is only as safe as the code that executes it

An engineering study of the execution boundary around Salus's documented /v1/decide API. A deliberately flawed integration and a corrected one face the same ten scenarios, and a seeded benchmark records which invariants hold.

The problem

Authorization holds only where side effects pass through it

Salus decides whether a proposed agent action should run. That decision protects nothing if the side effect can happen another way, with different arguments, after a failed check, or twice.

A second write pathAnother tool changes the same state with no decision.
Arguments that moveThe action executed is not the action that was decided.
Fail-open errorsA timeout or malformed answer is treated as permission.
Retries and duplicatesOne intended refund is paid more than once.

Salus's integration guide states the same principle: "If some tool calls hit Salus and others do not, you no longer have a trustworthy control plane." (docs)

    TypeScript adapter

    The /v1/decide client and decision validation

    • Copies only the documented fields (tool_name, tool_id, idempotency_key, agent_id, args, context, fields, mode) when called, then validates that copy. What is validated is what is sent.
    • Refuses locally, with no request, when tool_name, the required idempotency_key or args is missing.
    • A 2xx counts only if decision is exactly allow, block or escalate. Anything else, including revise from the marketing page, is malformed.
    • Retries only on 429, 503, timeouts and network errors, with the same body and key, up to maxAttempts. 400, 401, 403, 404, 409 and 422 are reported, never retried.
    • Never throws, enforces its timeout even if fetch ignores the abort, and redacts the API key from every result.

    Trusted boundary and audit

    What the corrected boundary guarantees, and how

    // src/integrations/protected.ts (excerpt)
const args = copyRefundArgs(raw);   // exactly 3 own keys, frozen
if (!args) return { status: "rejected", reason: "invalid_arguments" };
const key = refundIdempotencyKey(args);
let shared = inFlight.get(key);      // concurrent identical calls
if (!shared) {
  const started = decideThenExecute(args, key)
    .finally(() => inFlight.delete(key));
  inFlight.set(key, started);
  shared = started;
}
return shared.then((r) => ({ ...r }));

    An allowed key with no executed entry, for example after outcome_unknown, stays in pendingActions(). With a file, the log is append-only JSON lines and a restarted process reads earlier entries; a torn last line is marked, never silently dropped.

    Correctness mechanisms

    Retries, idempotency, concurrency, integrity, recovery

    ConcernWhat the code doesLimit
    RetriesBounded attempts on 429, 503, timeout and network only; same body and key. Retry-After is honoured; above our 60 s limit the 429 is returned rather than waiting less. Every retry is a new proposal to Salus.The retry policy is ours; the docs give none beyond Retry-After.
    IdempotencyKey refund:{order_id}:{amount_minor}:{currency}, derived from the action and sent to both the decision and the CRM.Action-derived keys merge two genuinely separate refunds of the same order, amount and currency into one. A real system would key on a caller-supplied request ID.
    ConcurrencyIdentical calls in one process share a single in-flight execution: one decision request, one refund.Per process only. Across processes the protection is the provider's idempotency.
    Argument integrityExactly order_id, amount_minor, currency (checked with Reflect.ownKeys), copied and frozen. The same bytes are decided, hashed and executed.Schema is fixed to this one tool.
    Failure handlingAnything except ok with allow means no refund. escalate is recorded as not executed, pending a human.No approval workflow: the raw-HTTP escalation follow-up is undocumented.
    RecoverySimulated: the synthetic CRM applies a refund and then throws, and the boundary records outcome_unknown. A new boundary instance over the same CRM and audit log retries, and the CRM replays the key, so one refund is paid in total.Not production crash recovery. No process was killed, the CRM is in memory, and there is no reconciliation against a real provider.

    Trade-offs and open concerns

    What a production integration would still need

    Enforcement location

    This is client-side enforcement around an advisory decision; the docs describe raw decide_only verdicts as advisory. It holds only if the boundary is the sole holder of the provider credential, or if Salus's SDK wrapper or proxy is used.

    Identity and keys

    Caller-supplied request IDs instead of action-derived keys; a real runtime key from a secret manager; a shadow-then-enforce rollout as the docs describe.

    Durability

    A durable, tamper-evident audit store with multiple writers, provider reconciliation for unknown outcomes, and outcome reporting (the HTTP decision ID field is undocumented).

    Escalation

    An approval workflow. The docs say approval "grants a one-time retry for the same payload"; how a raw HTTP client learns of it is not documented.

    Realistic next steps

    Run the same scenarios against a Salus test workspace in shadow mode (needs an account and key); add a real LLM agent behind the MCP-style server; replace in-flight sharing with a persistent idempotency store.

    Out of scope here

    A real LLM, a real Salus account or key, network calls, MCP-client compatibility, and production hardening. This is a reference example, not an SDK.

    Method and limits

    How the benchmark works

    • 10 scenarios × 2 integrations × 30 runs. Run r of scenario i uses a mulberry32 PRNG seeded with seed·1000003 + i·10007 + r, so both integrations see identical inputs.
    • Each run builds a fresh world: synthetic CRM, local mock, decide client (20 ms timeout, 2 attempts), audit log in memory.
    • A scenario is "held" only if its invariant held in all 30 runs. Correctness uses no clock and no Math.random, so a seed fixes the verdicts.
    • Decisions come from our mock's assumptions: allow up to 10,000 minor units, escalate up to 50,000, block above; same key and arguments replay the first decision.

    One known weakness: the args_tampered_after_decision invariant would also hold if nothing were paid. Acceptance test T3.4 separately requires the decided refund to execute.
