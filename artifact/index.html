The thesis

An authorization decision only protects the actions that actually pass through it. Authorization fails when a side effect can happen without it: by a second write path, with arguments that change after the decision, when the decision fails, or twice when a call is retried.

So the hard part of integrating a policy engine is not the API call. It is the execution boundary: the one place that turns an allow into exactly one effect, for exactly the action that was decided, and nothing otherwise.

  • Raw decide_only verdicts are "advisory". Hard enforcement is the SDK wrapper or Salus's proxy. TypeScript support is "coming soon".

This example ours

  • A TypeScript client for the documented request and response, which fails closed on anything undocumented.
  • A local mock of /v1/decide. Its refund thresholds, replay and fault injection are our assumptions, labelled in code.
  • A client-side boundary around an advisory decision. It is not Salus's enforcement and not an SDK.
  • A scripted, deterministic agent (no LLM), a synthetic CRM, and an MCP-style stdio server (no compatibility claimed).
  • Eight places where the docs are silent are flagged in decide-contract.md, not invented.

How the boundary holds

Retries

The client retries only on 429, 503, timeout and network errors, with the identical body and key and a bounded number of attempts. A Retry-After over 60 s returns the 429 instead of waiting. Each retry is a new proposal to Salus.

Idempotency

The key refund:{order}:{amount}:{currency} comes from the action alone, and it is sent to Salus and to the CRM. A duplicate is replayed, never paid twice.

Argument integrity

The boundary accepts exactly three fields (checked with Reflect.ownKeys), then copies and freezes them. The same object is decided, hashed into the audit log and executed.

Failure handling

If the audit log can't record the decision, nothing runs. escalate means not executed, pending a human, and approval leads to a re-decided retry.

Crash recovery

The provider can fail after paying. The key then stays pending in the append-only log. After a restart the retry is replayed by the CRM, so the refund is paid once in total.

Evidence

39 tests: 32 acceptance tests, 4 Retry-After tests, 1 determinism test, and a 2-part type check against a pinned compiler.

Trade-offs, limits, and what production needs

Deliberate trade-offs and limits

  • Client-side enforcement: it is only as strong as the guarantee that the agent cannot reach the CRM another way.
  • The key comes from the action: two genuinely separate identical refunds look like one.
  • In-flight sharing is per process; across processes, provider idempotency does the work.
  • The audit log is local: append-only by API, not tamper-evident, one writer.
  • Not covered: a real LLM, a real Salus account, network calls, MCP-client compatibility.

A real integration would add

  • A Salus runtime key from a secret manager, plus shadow-then-enforce rollout, as the docs describe.
  • The boundary as the only holder of the provider credential, or Salus's SDK wrapper or proxy.
  • Caller-supplied request IDs for idempotency.
  • An escalation approval workflow and outcome reporting to Salus.
  • A durable, tamper-evident audit store and multi-instance coordination.
